About

I'm a full-stack and backend developer working mainly in Go, TypeScript and Node.js, with PostgreSQL, Redis and Docker underneath. I build software around specific business problems — payment gateways, point-of-sale and inventory, real-time dispatch — and I focus on correctness under real conditions: payments that can't be credited twice, stock that can't be oversold, and services that keep working when a dependency fails.

I hold a B.A. in Public Administration, majoring in Sociology, from the University of Nairobi, and I put that training to work through civic technology aimed at the gaps that slow down public service delivery. Bunge Watch (opens in a new tab) explains parliamentary bills in plain English and Kiswahili and links citizens to the official comment process. A Public Participation Platform (opens in a new tab) lets residents comment on county bills and budgets by web, SMS or USSD, and records how each submission was considered. A Birth & Civil Registration Assistant (opens in a new tab) cuts wasted trips and queues with document checklists, deadline reminders and booked appointments. Knowing how public institutions actually work lets me design systems that fit their processes instead of working around them.

AuraRisk

Personal project · Sole developer

A climate-risk platform that gives communities localised flood risk, early warnings and community disaster reports, on the web and on mobile.

Problem
People in flood-prone areas need local, timely warnings, not just a regional forecast.
Approach
A Go API scores flood risk from Open-Meteo rainfall, soil moisture and weather codes, and serves community reports. A React web map and an Expo mobile app share one TypeScript client.
Key decision
Weather is cached per ~2 km grid cell with a stale-data fallback, and alerts are never sent from stale data. The score is labelled as a heuristic, with confidence capped at medium until it's calibrated.
Status
Pilot stage: not yet a safety-critical warning system. Security and reliability hardening is merged. Calibrating the risk model is next.

PayBridge

Personal project · Sole developer

An M-Pesa payments gateway that lets any app accept payments through one REST API — rate-limited, idempotent, and built so it can't double-credit a payment.

Problem
Safaricom's Daraja API is easy to integrate unsafely: STK push timeouts, duplicate callbacks, unsigned webhooks and expiring tokens all lead to lost or double-counted payments.
Approach
STK push with idempotency-key support, callback deduplication behind a forward-only payment state machine, a reconciliation job that recovers lost callbacks, and HMAC-signed merchant webhooks with exponential-backoff retries.
Key decision
Rate limiting runs as an atomic Redis Lua script, and merchant auth uses argon2id, 15-minute access tokens and refresh-token rotation with reuse detection.
Status
Live against the Daraja sandbox with Swagger docs. CI runs lint, type checks, a migration drift check and integration tests on real PostgreSQL and Redis.

TypeScript · Fastify · PostgreSQL · Redis · OpenAPI

Boda Dispatch

Personal project · Sole developer

A real-time delivery dispatch board where dispatchers and boda riders share one live view of every job, even when a rider's connection drops.

Problem
Riders on patchy mobile data send updates late, twice or out of order, and two dispatchers can grab the same job at once.
Approach
A Fastify server with Socket.IO and the Redis adapter, so live updates work across several server instances, and a Next.js dashboard sharing typed schemas with the server.
Key decision
Conflict handling is designed into the schema from day one: jobs carry a version for optimistic concurrency, and an append-only event log deduplicates replayed offline updates.
Status
In progress. Schema, health checks, CI and dispatcher auth with authenticated sockets are done; the live job board and offline rider queue are next.

TypeScript · Next.js · Fastify · Socket.IO · PostgreSQL · Redis
